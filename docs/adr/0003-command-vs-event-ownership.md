# ADR-0003. Состоянием Exception владеет exception-service; Resolution управляет им командами

Статус: принято.

## Контекст

Resolution знает, когда исключение пора перевести в работу или решить, но само исключение — агрегат другого сервиса.

## Варианты

| Вариант | Что даёт | Чем плох |
|---|---|---|
| Resolution пишет статус в БД exception-service | просто | общая база: связность по схеме, нет единого места для инвариантов |
| Синхронный REST `POST /exceptions/{id}/resolve` | немедленный ответ | недоступность exception-service останавливает workflow; нужна своя идемпотентность и retry |
| Exception слушает события Resolution и сам решает | слабая связность | lifecycle размазан: чтобы понять переход, надо читать два сервиса |
| **Команды через Kafka + inbox** | владелец один; отправитель не зависит от доступности получателя | согласованность в конечном счёте; отказ приходит асинхронно |

## Решение

Resolution пишет команды (`StartExceptionProgress`, `ResolveException`, `CloseException` …) в свой outbox,
exception-service применяет их через inbox и проверяет переход в агрегате `ExceptionRecord`. Недопустимая команда —
не ошибка инфраструктуры: публикуется `ExceptionCommandRejected`.

Владение контрактом: у `*.events` — продюсер, у `*.commands` и `*.queries` — потребитель.

## Последствия

- Между «Resolution решил» и «Exception в RESOLVED» есть задержка; API читает состояние у владельца.
- Отправитель должен уметь реагировать на отказ. Сейчас отказ только логируется и попадает в аналитику — это пробел.
