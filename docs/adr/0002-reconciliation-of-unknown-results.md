# ADR-0002. Reconciliation неизвестных результатов (UNKNOWN)

Статус: принято.

## Контекст

Часть вызовов внешних систем заканчивается без ответа. Повторить вслепую нельзя — действие может выполниться
дважды. Старый механизм (`@Scheduled` под ShedLock, счётчик проверок в самом `Action`, правило «видно старое
состояние → NOT_APPLIED → повтор») привёл к инциденту: внешняя система перевела запись на асинхронную обработку,
чтение отставало, и по части отправлений выполнились две повторные доставки.

## Варианты

| Вариант | Что даёт | Чем плох |
|---|---|---|
| Индекс и backoff поверх старого планировщика | мало изменений | технические поля остаются в `Action` и конкурируют с workflow за optimistic lock |
| **Отдельная `ReconciliationTask` + claim через SKIP LOCKED** | маленькая таблица со сроком, backoff и текущим запросом; работает на всех репликах | два источника состояния (Action и Task) — нужны инварианты |
| Отложенные сообщения через Kafka | нет polling | задачу нельзя отменить при позднем результате; не видно, сколько UNKNOWN сейчас |
| Temporal / Camunda | готовые таймеры и retry | новая платформа ради одной задачи |
| Reconciliation целиком в Integration | один сервис | «выполнено ли действие» — бизнес-решение, оно принадлежит Resolution |

## Решение

- `ReconciliationTask`: `READY → QUERYING → RESOLVED / ESCALATED / CANCELLED`; результат хранится отдельно от статуса;
  partial unique index — не больше одной активной задачи на попытку.
- Воркеры на всех репликах забирают задачи `FOR UPDATE SKIP LOCKED` и в той же транзакции пишут
  `QueryExternalState` в outbox.
- Защита от ложного `NOT_APPLIED`: первая проверка через `settleDelay`; подтверждение несколькими проверками
  подряд; там, где и этого мало, автоповтор выключен флагом и решение принимает оператор.
- Integration возвращает наблюдение, Resolution интерпретирует. Ответ на неактуальный запрос отбрасывается
  по `current_query_id`.
- Срок задачи; по истечении, а также при `INCONCLUSIVE` / `CONFLICT` — work item оператору.
- Поздний результат исходной команды завершает reconciliation; если он пришёл после второй попытки — `CONFLICT` и алерт.
- В Integration — раздельные пулы и доли rate limit для команд и запросов.
- Настройки на пару «система + тип действия» — таблица `reconciliation_policy`.

## Последствия

- Время до результата выросло (задержка и повторные проверки): безопасность выбрана важнее скорости.
- Больше ручной работы там, где автоповтор отключён.
- Polling БД в Resolution остался, но по маленькому partial-индексу активных задач.
- Rate limiter локальный в каждой реплике: фактический лимит = значение × число реплик.
- Для систем без запроса статуса по id остаётся риск двойного исполнения — он виден в метрике
  `reconciliation_false_not_applied_total`.
