# ADR-0001. Transactional Outbox + Debezium CDC в resolution-service

Статус: принято.

## Контекст

Изменение состояния в PostgreSQL и публикация сообщения в Kafka не должны расходиться. Resolution — центральный
узел: на одно исключение приходится порядка 15 исходящих сообщений, а при массовых сбоях поток растёт до сотен
в секунду. Polling-публикатор (SELECT pending → send → UPDATE) на всплесках отставал и сам стал заметной
нагрузкой на БД (постоянные SELECT/UPDATE, мёртвые строки, autovacuum).

## Варианты

| Вариант | Что даёт | Что усложняет / чем плох |
|---|---|---|
| Оставить polling и оптимизировать (partial index, batch) | минимум изменений | нагрузка растёт вместе с outbox; приложение остаётся механизмом доставки |
| LISTEN / NOTIFY | быстрый сигнал | это сигнал, а не очередь: теряется при реконнекте, SELECT всё равно нужен |
| Kafka transactions без outbox | нет лишней таблицы | не включают PostgreSQL в транзакцию — проблема «БД → Kafka» остаётся |
| INSERT + DELETE / `pg_logical_emit_message` | таблица не растёт | при потере слота событие нельзя опубликовать повторно |
| **Append-only outbox + Debezium** | приложение только пишет строку; доставка читает WAL последовательно и масштабируется отдельно | новая инфраструктура: слот, WAL, коннектор, их мониторинг |

## Решение

- `outbox` в resolution — append-only, без статуса; контракт таблицы описан в миграции `002-inbox-outbox.sql`.
- Один коннектор на БД, свой слот и публикация; Outbox Event Router: `destination` → топик, `aggregate_id` → ключ,
  метаданные → заголовки. Конфиг — `services/resolution-service/deploy/debezium/`.
- `snapshot.mode=no_data`: при первом старте история outbox заново не публикуется.
- Inbox у каждого потребителя: дубли от рестартов и повторной публикации не меняют состояние.
- Exception и Integration остаются на polling: их объём мал, перевод не оправдан. Это осознанная неоднородность.

## Последствия

- Появилось, что мониторить: lag и активность слота, состояние коннектора (алерты `ReplicationSlot*`).
- Остановленный коннектор удерживает WAL → на стороне PostgreSQL нужен `max_slot_wal_keep_size`.
- Outbox растёт → retention не короче окна повторной публикации (сейчас — периодический DELETE, на больших
  объёмах — партиционирование).
- Команда сервиса отвечает за схему outbox и наблюдаемость коннектора, даже если Kafka Connect ведёт платформа.
- Обнаружено на стенде: без топика `__debezium-heartbeat.<prefix>` при выключенном auto-create коннектор молча
  перестаёт публиковать.

## Не реализовано в этом репозитории

Миграция через shadow topic (сверка CDC со старым публикатором до переключения) и повторная публикация после
потери слота через incremental snapshot с условием по `created_at`.
