# Отличия от исходного описания и границы реализации

Источник сравнения — предоставленный PDF с описанием системы. Ниже три списка: что изменено намеренно,
что не реализовано, и что написано, но не проверено запуском.

## 1. Изменено относительно описания

| # | В описании | Здесь | Причина | Цена решения |
|---|---|---|---|---|
| 1 | Java 17, Spring Boot 3.2 | Java 21, Spring Boot 3.5.7 | Линейка 3.2 вышла из бесплатной поддержки (по моим данным — в конце 2024; проверьте на spring.io). В 3.4+ есть встроенные JSON-логи (`logging.structured`) | Версии отличаются от «боевых» из описания |
| 2 | У каждого сервиса свой репозиторий | Монорепозиторий, многомодульный Maven | Одна ветка для работы; проще читать целиком | Не видны настоящие проблемы multi-repo: версионирование общей библиотеки, независимые релизы, пайплайн на сервис. Как разрезать — в [ci-cd.md](ci-cd.md) |
| 3 | Трейсинга нет, цепочки по correlationId | Добавлен OpenTelemetry (Micrometer Tracing → OTLP); `traceparent` хранится в outbox и переживает CDC | В описании это названо болью («проблемы видны по жалобам») | Ещё одна инфраструктура (collector, хранилище трейсов) |
| 4 | «Запросы и команды в разных пулах» (топики не уточнены) | Два топика: `integration.commands` и `integration.queries` | Разные listener-контейнеры = разные пулы потоков; lag виден раздельно | Нет общего порядка между командой и запросом (он и не нужен) |
| 5 | Inbox в каждом сервисе | В integration роль inbox играет PK `integration_operation` (id приходит в команде); в analytics — PK `raw_event` | Естественный ключ уже есть; отдельная таблица дублировала бы его | Механизм не единообразен между сервисами |
| 6 | Не описано, как сопоставить поздний результат команды, HTTP-ответ на которую потерян | В результат внешней системы добавлено эхо `idempotencyKey` | Без этого поздний результат для UNKNOWN не с чем сопоставить | Требование к контракту внешней команды |
| 7 | IntegrationEndpointPolicy — сущность | `@ConfigurationProperties` (`integration.systems.*`) | Технические параметры меняются выкладкой, а не оператором | Нельзя поменять без рестарта |
| 8 | Сущность `Exception` | Класс `ExceptionRecord`, таблица `exception_record` | Конфликт имени с `java.lang.Exception` | Расхождение кода с языком предметной области |
| 9 | Не описано поведение при команде, не подходящей к состоянию | Событие `ExceptionCommandRejected`, а не DLT | Ретрай такой команде не поможет, а партицию заблокирует | Отправитель обязан обрабатывать отказ (сейчас он только логируется/попадает в аналитику) |
| 10 | «При открытом circuit breaker систему не опрашивают» | Integration сразу отвечает `ExternalStateQueryFailed(CIRCUIT_OPEN)`, Resolution откладывает проверку с backoff | Resolution не должен знать состояние breaker-а чужого сервиса | Один «холостой» круг через Kafka на каждую проверку |
| 11 | Retention outbox — партиционирование по времени | Периодический `DELETE` старше `resolution.outbox.retention` | Проще; при учебных объёмах достаточно | Мёртвые строки и нагрузка на autovacuum; на объёмах из описания нужно партиционирование |
| 12 | Секреты «берутся из Vault» (механизм не указан) | External Secrets Operator: Vault → Secret → env | Самый распространённый вариант без sidecar | Нужен оператор в кластере; альтернативы — Vault Agent Injector, CSI driver |
| 13 | Правила окончательного закрытия не описаны | `RESOLVED → CLOSED` после «тихого периода» (`exceptions.closing.quiet-period`) | Нужно было выбрать правило | Правило выдумано, а не взято из бизнеса |

Обнаружено при запуске на стенде (в описании нет): при выключенном авто-создании топиков Debezium **молча
останавливается** на первом heartbeat, если не создан топик `__debezium-heartbeat.<topic.prefix>`. Топик добавлен
в `scripts/create-topics.sh` и `deploy/platform/kafka-topics.yaml`.

## 2. Не реализовано

- `ProblemCase` / `ProblemCaseException` (группировка исключений в кейс). Связи `ExceptionRelation` есть.
- `WorkflowDefinition` / `WorkflowStep`: workflow — зашитый автомат «одно действие → верификация», а не шаблон.
- `SlaPolicy` как сущность и `SlaPauseInterval` (паузы SLA, часовые пояса); SLA — один дедлайн из политики.
- `EscalationPolicy` как сущность: эскалация одна — по нарушению SLA.
- Адаптеры OMS, WMS, CRM: есть только Delivery (REST). Интерфейс `ExternalSystemAdapter` — точка расширения.
- Аутентификация и авторизация REST API, маскирование персональных данных в логах.
- Операторский интерфейс (frontend).
- Отдельный репозиторий автотестов QA (RestAssured).
- Миграция через shadow topic, incremental snapshot после потери слота — описаны в [ADR-0001](adr/0001-transactional-outbox-cdc.md), кода нет.
- Безопасность Kafka (TLS, SASL, ACL), schema registry.
- Patroni / отказоустойчивый PostgreSQL: локально один экземпляр.
- Fluent Bit → OpenSearch: сервисы пишут JSON (ECS) в stdout, сборщик и хранилище логов в compose не включены.
- Метрики из раздела аналитики: recurrence, cascade frequency, время реакции оператора.

## 3. Что чем проверено

| Что | Проверено | Не проверено |
|---|---|---|
| Сервисы и библиотеки | `mvn verify`: unit + интеграционные тесты на Testcontainers (PostgreSQL, Kafka, WireMock), порог JaCoCo | Нагрузка; несколько реплик одновременно; отказ брокера или БД посреди работы |
| Сквозной поток через Debezium | Локальный стенд в контейнерах: happy path до `CLOSED / VERIFIED`; `TIMEOUT-*` → UNKNOWN → сверка → `APPLIED` без повторной команды; заголовки сообщений, выставленные Event Router | Сценарий `TIMEOUT-STALE-*` досмотрен только до второй проверки подряд (`NOT_APPLIED`, streak 2), до второй попытки не дожидался; потеря слота, failover PostgreSQL, рестарт коннектора под нагрузкой |
| Dockerfile | Образы всех четырёх сервисов собраны и запущены через `docker compose --profile apps` | Сканирование Trivy; сборка в CI |
| Метрики и алерты | Prometheus на стенде: 16 правил в состоянии `ok`; имена метрик из выражений алертов найдены у живых экспортёров (`pg_replication_slots_*`, `kafka_consumergroup_lag`) и сервисов; `promtool check rules` | Срабатывание алертов (ни один не доводился до `firing`); пороги не калибровались; доставка в Mattermost (URL — заглушка) |
| Трейсы | Jaeger на стенде: один трейс проходит все четыре сервиса, включая HTTP-вызов внешней системы | Сэмплирование меньше 1.0; OTel Collector между сервисами и хранилищем |
| Дашборд Grafana | Загружается через provisioning (папка DEMP) | Панели глазами не просматривались: возможны пустые графики и неудачные единицы |
| Helm-чарт | `helm lint --strict` и `helm template` для 4 сервисов × 4 окружений | Не применялся к кластеру; CRD (ServiceMonitor, ExternalSecret) не валидировались по схемам; probes, graceful shutdown и NetworkPolicy в кластере не проверялись |
| `deploy/platform/*.yaml` (Strimzi, PrometheusRule) | Синтаксис YAML; сверка с источниками скриптами | Не применялись; имена кластеров и путь к секретам — заглушки |
| GitHub Actions | Синтаксис YAML | Пайплайн ни разу не запускался |
| `.gitlab-ci.yml` | Синтаксис YAML | Не запускался; не проходил GitLab CI Lint |
| Kafka UI, Alertmanager в compose | Alertmanager стартует | Kafka UI не запускался (образ из ghcr.io был недоступен в среде разработки) |

Среда, в которой всё это писалось и запускалось, — изолированный контейнер без Kubernetes и без доступа к CI.
Поэтому первые два практических шага у себя: запустить пайплайн и развернуть чарт на kind / minikube.

## 4. Дефекты, найденные запуском (и исправленные)

Список полезен как иллюстрация того, что не ловится чтением кода.

| Где проявилось | Дефект | Исправление |
|---|---|---|
| Интеграционный тест exception-service | изменения сущности после `save()` терялись: при примитивном `@Version long` Spring Data считает сущность с заполненным id существующей и делает `merge` (возвращает копию) | `@Version Long` — `null` означает «новая» |
| Интеграционный тест integration-service | ответ 202 без `Content-Type` превращался в UNKNOWN: клиент не мог разобрать тело | тело читается строкой и разбирается терпимо: 2xx — это принятая команда |
| Интеграционные тесты integration-service | circuit breaker, открытый одним тестом, ломал следующий | параметры breaker-а вынесены в настройки; поведение проверяется отдельным unit-тестом |
| Стенд с Debezium | коннектор `RUNNING`, но outbox не публикуется: нет heartbeat-топика при выключенном auto-create | топик создаётся явно |
| Стенд | группы потребителей назывались по id слушателя, а не по сервису | явные `groupId` вида `<сервис>.<поток>` |
| Jaeger | трейс рвался на polling-outbox: наблюдаемый `KafkaTemplate` перезаписывал сохранённый `traceparent` контекстом потока планировщика | relay публикует через отдельный ненаблюдаемый template; тест на сохранение заголовка |
| Jaeger | каждый тик фоновых задач создавал отдельный трейс | наблюдение за `@Scheduled` отключено |
| Prometheus | при запуске сервисов в контейнерах метрики собирались дважды | один job через опубликованные порты |
