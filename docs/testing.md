# Тесты и покрытие

## Уровни

| Уровень | Где | Инструменты | Что проверяет | Запуск |
|---|---|---|---|---|
| Unit | `*Test.java` | JUnit 5, AssertJ | доменные инварианты без Spring: автомат статусов, backoff, интерпретация наблюдений, классификация транспортных ошибок, circuit breaker | `make unit` (Docker не нужен) |
| Интеграционные | `*IT.java` | Spring Boot Test, Testcontainers (PostgreSQL, Kafka), WireMock, Awaitility | сервис как чёрный ящик: сообщение в Kafka → строки в БД и outbox; запись outbox в одной транзакции с изменением; inbox и дубли; DLT; задержка ответа WireMock воспроизводит UNKNOWN | `make verify` |
| Стенд | вручную | docker-compose, Debezium | полный путь через CDC | [local-development.md](local-development.md) |

Разделение `*Test` / `*IT` сделано плагинами surefire / failsafe: быстрые тесты можно гонять отдельно, а упавший
интеграционный тест не мешает получить отчёт по unit-тестам.

Что интеграционные тесты **не** проверяют: участок outbox → Debezium → Kafka в resolution-service. В тестах контрактом
считается строка в `outbox`; сам CDC проверяется только на стенде. Это ограничение есть и в исходном описании
проекта («полный путь через Debezium — только на dev и test»). Альтернатива — поднимать Debezium в Testcontainers
(`debezium-testing-testcontainers`): даёт проверку конфига коннектора в пайплайне, стоит +1–2 минуты на прогон.

## Что стоит прочитать в тестах

| Тест | Чему учит |
|---|---|
| `InboxOutboxIT` (platform-common) | откат транзакции убирает и бизнес-строку, и outbox; сбой обработчика откатывает inbox |
| `ExceptionFlowIT` | техническая и бизнес-дедупликация, команды и их повторная доставка, отказ команды, DLT |
| `ResolutionFlowIT` | весь сценарий UNKNOWN: подтверждение NOT_APPLIED, устаревшие ответы, поздний результат и CONFLICT, срок задачи, флаг автоповтора |
| `IntegrationFlowIT` | read timeout → UNKNOWN без повтора; 503 → транспортный retry; повторная доставка команды; операция, прерванная падением |
| `AnalyticsIT` | события приходят не по порядку и с дублями, а модель остаётся верной |

## JaCoCo

- Агент подключён к обоим наборам тестов и пишет в один `target/jacoco.exec`.
- На фазе `verify`: отчёт (`target/site/jacoco/index.html`, `jacoco.xml` для Sonar) и проверка порога.
- Порог — **60% строк на модуль** (`jacoco.minimum.line` в корневом `pom.xml`); при меньшем покрытии сборка падает.
- `make unit` (`-DskipITs`) проверку порога отключает: без интеграционных тестов цифра не имеет смысла.
- Модуль `contracts` исключён: в нём только записи без логики.

Порог 60% повторяет «общее около 60%» из описания проекта. Требование «≥70% на новый код» в Maven выразить нельзя:
это quality gate SonarQube, он сравнивает с предыдущим анализом (джоб `sonarqube` в пайплайне).

Покрытие — показатель того, какие строки исполнялись, а не того, что поведение проверено. Высокая цифра здесь
получена в основном интеграционными тестами, которые проходят код насквозь.

```bash
python3 scripts/coverage-summary.py
```
